# Установка, конфигурация и обновление Enterprise Control Center (ECC)

Руководство описывает развёртывание, настройку переменных окружения, резервное копирование перед обновлением, процедуру обновления и проверку готовности ECC в standalone-контуре Node.js / Express + Vite.

## 1. Требования к окружению

- Node.js 22 LTS или новее
- `npm` 10+
- Минимум 512 МБ RAM и выделенный том/каталог для постоянного хранения состояния (`ECC_DATA_DIR`, по умолчанию `./data`)
- TLS reverse proxy (Nginx / Caddy / Envoy / балансировщик) перед приложением для терминирования HTTPS в production-пилоте

## 2. Первичная установка

1. Клонируйте репозиторий и установите зависимости:
   ```bash
   npm ci
   ```
2. Подготовьте переменные окружения (на основе `.env.example`):
   - `ECC_SECRET_KEY` — уникальный случайный ключ длиной от 32 байт (`openssl rand -hex 32`).
   - `ACCESS_TOKEN_MINUTES` — время жизни Bearer-токена в минутах (`5..60`, по умолчанию `20`).
   - `AUTH_RATE_LIMIT_MAX` / `AUTH_RATE_LIMIT_WINDOW_SECONDS` — лимит попыток входа с одного `X-Real-IP` (по умолчанию `10` попыток за `60` секунд).
   - `CORS_ORIGINS` — точный список разрешённых HTTPS-origins через запятую (значение `*` запрещено).
   - `ECC_DATA_DIR` — каталог для `ecc_store.json` и подкаталога `backups/`.
   - `ECC_BACKUP_RETENTION_COUNT` — количество хранимых локальных снимков на организацию (`1..100`, по умолчанию `10`).
   - `ECC_STRUCTURED_LOGS` — установите `true` для вывода структурированных JSON-логов HTTP-запросов в `stdout`.
3. Соберите клиентскую часть и проверьте типы и автотесты:
   ```bash
   npm run lint
   npm run build
   npm test
   ```
4. Запустите сервер:
   ```bash
   NODE_ENV=production npm start
   ```
   Проверка доступности: `GET /health` возвращает `200 OK` (`{"status":"ok"}`).

> При первом запуске на пустом `ECC_DATA_DIR` создаётся начальный администратор (`admin@example.com`). Немедленно смените его пароль после первого входа через интерфейс профиля или `POST /api/v1/auth/change-password`.

## 3. Процедура перед обновлением

1. Создайте снимок резервной копии в разделе **«Резервные копии»** (`POST /api/v1/system/backup/snapshots`) или выгрузите `.json` дамп (`GET /api/v1/system/backup`) с заголовком `X-ECC-Backup-SHA256`.
2. Убедитесь, что локальный снимок имеет статус `SHA-256 подтверждён`, а проверка **Dry-Run** (`POST /api/v1/system/backup/verify`) проходит без ошибок.
3. Сохраните резервную копию и файл `${filename}.sha256` на внешнем носителе за пределами хоста.

## 4. Обновление версии

1. Остановите процесс приложения (`systemctl stop ecc` или остановка контейнера), чтобы исключить запись в `ecc_store.json` во время обновления.
2. Получите новый релиз кода и обновите зависимости:
   ```bash
   npm ci
   npm run lint
   npm run build
   ```
3. Запустите интеграционные тесты на изолированной копии:
   ```bash
   npm test
   ```
4. Запустите обновлённый сервис и проверьте:
   - `GET /health` → `200 OK`;
   - раздел **«Мониторинг и диагностика»** → отсутствие критических алертов (`http_5xx`, `corrupted_snapshot`) и статус параметров в **«Чек-листе готовности к эксплуатации»**.

## 5. Откат и учения по восстановлению (DR Drill)

Если после обновления обнаружена регрессия:

1. Остановите новую версию, верните предыдущий релиз кода и при необходимости восстановите `ecc_store.json` через `POST /api/v1/system/restore` (сервер автоматически сверяет SHA-256 до записи данных).
2. Зафиксируйте метрики восстановления в разделе **«Учения по восстановлению (Recovery Drill Report)»** (`POST /api/v1/system/recovery-drills`), указав временные метки инцидента, старта и завершения восстановления с часовым поясом (`Z` или `±HH:MM`), а также при наличии — метку последней подтверждённой транзакции для точного расчёта RPO.
